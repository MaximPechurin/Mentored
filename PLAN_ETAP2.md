# Этап 2: Образовательная платформа (Школа)

> Источник: ТЗ `Mentored_образовательная_платформа_и_сайт.docx`, раздел
> «6. План разработки по этапам» → ЭТАП 2 (6 недель / 42 дня, может идти
> параллельно с Этапом 1).
>
> Цель этапа: полнофункциональная платформа управления курсами — студенты
> смотрят купленные курсы, сдают домашние задания, менторы их проверяют,
> доступ открывается автоматически после оплаты.

Статус на 31.07.2026: Этап 1 (MVP сайта) выпущен как v1.0 и работает в
проде. По Этапу 2 в `backend/school/` (бывш. `lms`, переименовано в
чате) готова база данных: учебные курсы, роли, доступ, домашние задания.
Дальше по списку — хук «оплата → доступ», API, фронт, интеграции,
тестирование.

## Архитектурные решения (зафиксировано в чате)

**Feature-gate `User.is_dev`** — раздел «Школа» можно выкатить на прод
закрытым: его видят только пользователи с галкой `is_dev` (ставится в
админке) и суперюзеры. Гейт двойной — и на фронте (кабинеты/страница
курса и ссылки в шапке скрыты, редирект на главную), и в API (permission
`school.permissions.IsDev` на всех school-эндпоинтах, иначе URL можно
угадать). Когда школу откроют для всех — снять `IsDev` со school-вью и
убрать `is_dev`-условия на фронте; само поле можно оставить.

**Приложение называется `school`**, не `lms` — переименовано по
запросу, никакой другой смысл в это не вкладывался. Внутри той же
Django-задачи (один бэкенд, одна БД), просто отдельная папка/домен для
учебной части, чтобы не трогать `mentored` (каталог/корзина/заказы/
Mercado Pago) при доработках учебного функционала.

**Роли пользователей** — отдельная модель `mentored.Role` (не
`choices`), у `User` — `ManyToMany` к `Role` (`user.roles`), т.к. один
человек может совмещать роли (например, ментор, проходящий чужой курс
как студент). Код опирается на фиксированные `codename`
(`Role.STUDENT='student'`, `Role.TEACHER='teacher'`) через
`user.has_role(codename)` / `user.is_teacher` / `user.is_student` —
новые роли можно заводить из админки без миграций, но прав они дают
ровно столько, сколько под них написано проверок в коде. `student`/
`teacher` сидируются миграцией `mentored/migrations/0007_seed_roles.py`.

**Учебный курс — самостоятельная сущность `school.Course`**, отдельная
от товара `mentored.Course` (витрина/цена/Mercado Pago, не трогаем).
Модули/уроки/прогресс/задания висят на `school.Course`. Так же курс
может существовать и без привязанного товара (бесплатный/ещё не
выставленный на продажу).

**Связь товар → учебный курс — `school.ProductCourseAccess`**, а не
жёсткий FK. Товар — generic (`ContentType` + `object_id`, тем же
способом, что уже использует `mentored.CartItem`), поэтому:
  - один товар может открывать сразу несколько курсов (например,
    Membership → доступ ко всем текущим курсам)
  - несколько разных товаров могут вести к одному и тому же курсу
    (акционный бандл)
Явно рассмотрели и отклонили вариант «настройка на уровне категории
товара, что к ней можно привязывать» — избыточно: во-первых, у товаров
сейчас нет единой сущности «категория» (Book/Course/Consultation/
Membership — разные модели), во-вторых, opt-in через конкретные строки
`ProductCourseAccess` уже даёт нужную гибкость без слоя настроек поверх.

**Профиль преподавателя** — `school.TeacherProfile` (фото/специализация/
био, `is_public=False` по умолчанию — публичная карточка ментора это
уже Этап 3 по ТЗ, но модель делаем сейчас, чтобы не переделывать). Кто
ведёт какой учебный курс — `school.CourseTeacher`.

      логируются — сохранение заказа/вебхук не роняются. Провалидировано

- [ ] Удобная привязка «товар → курс» в админке при создании товара

- [x] Проставление роли `student` пользователю при регистрации

- [x] Права в админке по ролям: ментор (роль `teacher`, не суперюзер)

- [x] Страница «Mis cursos» (`/escuela/estudiante`) — реальные данные

- [x] Видеоплеер — YouTube/Vimeo ссылки конвертируются в embed

**Кабинет ментора (`/escuela/profesor`) — первая рабочая версия готова:**
- `GET /school/teacher/courses/` — мои курсы (по `CourseTeacher`) со
  счётчиками студентов и сдач на проверку
- `GET /school/teacher/courses/<id>/students/` — ростер студентов курса
  с прогрессом (%, пройдено/всего); только для ментора этого курса (403)
- Фронт: список курсов, по клику раскрывается ростер с прогресс-барами,
  плюс блок «Tareas por revisar» (очередь ДЗ)
Полный цикл провалидирован сквозной эмуляцией через реальные эндпоинты
(2 студента покупают → проходят 25%/100% → преподаватель видит ростер).
Дальнейшее наполнение (что ещё показывать/делать ментору) — по фидбэку
заказчика (см. вопросы ниже).

## Форум, личные сообщения, аналитика (бэкенд) — из раздела 3 ТЗ

Сделано (модели `school/models.py`, миграция `0002`, API под `/school/`,
провалидировано смоук-тестом через эндпоинты):

- **Форум курса** (публичные обсуждения): участники = активные студенты
  курса + преподаватели курса (посторонний → 403).
  `GET/POST /school/courses/<id>/threads/`, `GET /school/threads/<id>/`,
  `POST /school/threads/<id>/posts/`, `POST /school/threads/<id>/moderate/`
  (pin/lock — только препод). В закрытой теме отвечает только препод.
- **Личные сообщения 1:1** — только студент↔преподаватель с ОБЩИМ
  курсом (`can_direct_message`); студент↔студент запрещён.
  `GET /school/messages/` (диалоги + непрочитанные),
  `GET/POST /school/messages/<user_id>/` (переписка + отправка, чтение
  помечает входящие прочитанными).
- **Аналитика (read-only)**:
  `GET /school/teacher/courses/<id>/analytics/` — по курсу для препода
  (студенты, средний прогресс, завершили/в процессе/не начали,
  статистика ДЗ); `GET /school/analytics/overview/` — общая по
  платформе, только суперюзер.
- Фронта для форума/ЛС/аналитики пока нет — только бэкенд (по задаче).

По ТЗ раздел 6 форум и расширенная аналитика формально относятся к
Этапу 3, но база готова уже сейчас.
